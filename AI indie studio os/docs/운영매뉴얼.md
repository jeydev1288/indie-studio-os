# Studio 운영 매뉴얼

## 요청 처리

1. 목표·대상·제약·산출물과 기존 문서를 확인한다. 중요한 누락은 묶어서 질문하고, 독립적으로 가능한 안전 작업은 진행한다.
2. 완료 기준, 의존성, 승인 여부와 필요한 역할을 정한다. 단순 요청은 바로 처리하고 복잡한 요청은 짧게 계획을 남긴다.
3. 독립적인 조사나 검토만 병렬로 분리한다. 위임 계약에는 목표, 맥락, 범위, 파일 소유권, 입력, 결과물, 검증 및 제약을 포함한다. 도구 미지원 시 순차 수행한다.
4. 결과를 총괄이 검토하고 적합한 실제 테스트를 수행한다. 실패는 원인 조사 후 수정하고 다시 확인한다.
5. 프로젝트 현황과 필요한 결정·오류·근거를 기록하고 한국어로 결과, 검증, 한계, 다음 행동을 보고한다.

## 상태와 전환

`IDEA → RESEARCH → VALIDATE → PLAN → BUILD → VERIFY → LAUNCH → OPERATE`를 기본으로 하며 `HOLD`, `PIVOT`, `ARCHIVED`를 별도 상태로 쓴다. 상태 변경 시 근거, 날짜, 담당과 다음 행동을 남긴다. VALIDATE는 고객 수요를 입증한 상태가 아니라 검증 활동 단계다. 출시나 외부 공개는 사용자 승인과 실제 검증 후에만 진행한다. 다른 제품 흐름은 필요할 때 프로젝트 문서에서 구체화한다.

## 승인과 보안

배포, 공개, 유료 서비스·금전 약정, 결제 설정, 외부 메시지, 중요 데이터 삭제, 민감한 개인정보 변경 및 주요 아키텍처 교체는 구체적인 결과물을 준비한 뒤 사전 승인받는다. 조용함은 승인이 아니다. 키·개인정보를 파일이나 보고서에 복사하지 않는다. 권한이나 도구가 없으면 우회하지 않고 차단 내용을 기록한다.

## 오답에서 개선까지

오류의 원인을 조사하고 재현과 수정이 확인되면 `docs/MISTAKES.md`에 증상, 영향, 근거, 원인, 조치와 검증 결과를 적는다. 미확인 원인은 가설로 남긴다. 교훈을 공통 매뉴얼로 승격하려면 원인과 수정이 검증되고 다른 작업에도 적용할 근거가 있어야 한다. 변경 대상·근거·검증·되돌리는 방법을 결정 기록에 남긴다. 한 번의 실패를 전역 규칙으로 일반화하지 않는다.

## 기록 관리

`docs/PROJECT_STATUS.md`는 전체 진행 상황의 진입점이며 `projects/registry.md`는 프로젝트별 상세 기록이다. 각 프로젝트의 실제 저장소를 임의로 변경하지 않는다. 조사 시 `research/saas-10-실험.md`의 근거 규칙을 적용한다. 기록은 세션 중 작업한 에이전트가 갱신하며 자동 동기화되지 않는다.
