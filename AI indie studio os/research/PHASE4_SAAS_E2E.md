# Phase 4 E2E: 인디 개발자 SaaS 아이디어 3개

조사일: 2026-11-06. 테스트 요청: “인디 개발자를 위한 작은 SaaS 아이디어 3개를 조사하고, 가장 유망한 아이디어를 선정해 MVP 개발 계획까지 작성해 줘.” 구현·배포·고객 접촉은 하지 않았다. 고객 수요, 지불 의사, 차별화와 수익은 검증되지 않았다.

## 선정안의 MVP 가설

독립 개발자가 프로젝트와 승인된 GitHub 저장소를 연결하고 설치 코드를 웹앱에 넣는다. 사용자는 제목·설명과 선택적 URL을 확인하고 제출한다. 서버는 입력과 요청 속도를 검증하고 지정 저장소에 이슈를 만든 뒤 성공이나 실패를 표시한다. GitHub App의 최소 권한을 우선 검토하되 구현 전 공식 문서와 실제 권한을 확인한다.

- 포함: 단일 저장소 연결, 설치 코드, 제출 폼, 서버 입력 검증, 제한, 이슈 생성과 오류 상태.
- 제외: 스크린샷, 자동 개인정보 수집, AI 분류, 다중 저장소, 공개 로드맵 및 실제 결제.
- 수용 기준: 무효 요청은 생성하지 않음; 정상 요청·중복 제출·GitHub 응답 유실과 재시도에서 중복 및 누락을 테스트; 불명확한 생성 결과를 무작정 재시도하지 않고 재조정; API 장애를 사용자에게 표시; 키는 브라우저에 노출하지 않음. 멱등 키와 상태 저장·재조정 방식은 구현 전에 설계해야 하며 정확히 한 번 생성을 이미 보장한다고 가정하지 않는다.
- 개인정보 기준: 자유 텍스트와 URL에도 개인정보가 들어갈 수 있음을 제출 전에 안내한다. URL의 쿼리와 조각 제거 여부, 데이터 보존·삭제 기준을 설계하고 실제 데이터 흐름과 수집 범위를 테스트한다.
- 구현 순서: 문제와 지불 의사 확인 계획 → 데이터 흐름·동의·GitHub 권한 설계 → 서버 검증과 이슈 생성 → 위젯과 오류 처리 → 남용 방지·보안·통합 테스트.
- 미확인: 고객의 불편 빈도, 무료 대안 대비 유료 가치, 획득 채널, 운영 비용, 개인정보와 GitHub 권한 요구. 고객 연락이나 배포에는 별도 승인이 필요하다.

## 수행 내역

총괄이 목표와 범위를 정했고 일반 하위 에이전트가 Researcher로 웹 조사 후 같은 에이전트가 Strategist·Product Manager 역할을 순차 수행했다. 다른 일반 하위 에이전트가 출처와 문서를 독립 검토했고, 총괄이 중복 처리·개인정보·무료 경쟁사 관련 지적을 반영했다. 프로젝트 TOML 역할로 실행한 것은 아니다. QA 검토와 보완 결과는 `docs/PHASE4_VALIDATION.md`에 기록한다.
